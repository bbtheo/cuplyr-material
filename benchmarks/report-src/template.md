## Read this first: what the numbers are

**What cuplyr's number is.** The cuplyr timing is the **computation on a table that is already on the GPU**: `r <- compute(mutate(gt, r = roll_mean(x, n)))` followed by a one-row device-to-host copy as a fence, with `gt <- tbl_gpu(df)` built once outside timing. By decision (Theo, 2026-10-21) it contains **no upload and no `collect()`**. The CPU packages operate on an R vector already in memory, so both sides time the computation only. A real pipeline that starts and ends in R would also pay the PCIe transfers that are excluded here (not measured in this study). The one exception is the median: `cuplyr (CPU fallback)` downloads, loops in R and re-uploads, and is *not* computation-only.

**What the CPU numbers are: measured thread behaviour, not settings.** Package thread settings do not say what a call did, so each multi-thread-capable entry (data.table, RcppRoll, roll) was timed twice, at its default setting and with its threads set to 1 (entries labelled `(1 thread)`), and the "Threads actually used" section reports both. The result:

- **RcppRoll runs on 24 OpenMP threads by default** (`RcppRoll::roll_threads()` = 24) and scales with them: 9-14x slower at one thread for every statistic at w=101.
- **data.table's `frollmean/sum/min/max/sd` and its `by=` evaluation ran effectively on one thread** (default vs `setDTthreads(1)` within 3.3%), although `getDTthreads()` is 12. Only `frollmedian` (2.3x), `frollsum(algo = "exact")` (5.0x) and `frollapply` (1.7x) scale.
- **roll ran effectively on one thread** for every statistic (1-thread vs default within 1% at w=101), although RcppParallel reports 24 available threads. (roll.so also imports OpenMP symbols, which `setThreadOptions()` does not govern; the default online vector workers used here are sequential loops, and only roll's offline workers are RcppParallel workers, so the one-thread reading holds.)
- RollingWindow, slider, zoo and runner were not given a thread control: their compiled code imports no OpenMP or TBB runtime symbol (`nm -D --undefined-only` on the installed `.so`; this check is not part of the script) and runstats is pure R. I treat them as single-threaded; that is a static check, not a timing.

So there is no blanket "GPU against N CPU threads" framing in this report: the comparison is to the per-entry thread behaviour above. Medians are reported with their spread (IQR in the tables, all samples in `timings.csv`). No headline speedup is claimed.

**What the cuplyr number still includes, per call.** R dispatch of `mutate()`/`compute()`, the AST node builds and schema inference, lowering to C++, **three full-table materializations** (an eager window `mutate()` runs a window node, a mutate node and a select node, each of which builds a new table, so the input column `x` is deep-copied three times per call; see "Per-call cost breakdown"), allocation of the results and their validity masks, and the fence. The same call on a 1e3-row table, where kernel time is negligible, takes about 2.0 ms for window functions (a plain `mutate(y = x + 1)` takes 1.3 ms). That ~2.0 ms floor is about 70% of the 2.78 ms measured at 1e6 rows / width 11 and larger than the whole data.table call (1.36 ms). The copy and allocation part grows with the row count and is **inside every 1e6 and 1e7 cuplyr timing** but not in the 1e3-row floor.

## Method

- Data: `set.seed(12345); x <- rnorm(1e6)`, no NAs, widths 11 / 101 / 1001, right-aligned, output the same length as the input, `NA` padded. Same functions and arguments as the post (see `rw_functions()` in `bench/rolling-lib.R`), `times = 20`, `times = 5` for the custom function.
- **Deviation 1, one harness for everyone.** The post used `microbenchmark(times = 20)`, which interleaves expressions and does not force a GC. Here every function (CPU packages and cuplyr) goes through `rw_time()`: untimed warmup calls, then `times` samples; an untimed `gc()` runs before every call with the previous result already dropped; each sample is timed with `microbenchmark::get_nanotime()`. cuplyr needs the `gc()`: an eager `mutate()` holds its GPU intermediates until R finalizes their pointers (finding F1), and twenty back-to-back 1e7-row calls without it ran the 12 GB card out of memory. Applying the same `gc()` to everyone keeps the comparison symmetric. Consequence: no GC ever lands inside a timed region, which in the post's interleaved harness it sometimes did, and deallocation of each result is untimed for every engine (cuplyr's GPU tables are freed with cudaFree inside that untimed `gc()`; the CPU packages' vectors likewise). A new test (`tests/testthat/test-bench-F54-harness-extra.R`) pins that `gc()` runs before every call and outside the timed region.
- **Deviation 2, GPU completion.** cuplyr's API gives no "work finished" guarantee (no `cudaDeviceSynchronize()` in `src/`). The timed closure ends with `cuplyr:::gpu_head(ptr, 1L, names)`, a one-row pageable copy to the host that synchronizes the stream (well under 1 ms; the PM measured 1e7 rows / width 101 / mean at 10 ms with the fence and 9 ms without).
- **Deviation 3, slow cells get fewer samples** (`CELL_BUDGET` = 20 s of timed work per cell). Each cell starts with one cold probe call; its duration sets the sample count through `rw_plan_cell()` (`bench/rolling-lib.R`). The probe call is *not* a recorded sample (unless it alone exceeds `PROBE_LIMIT` = 60 s, which no cell did); warmup calls (2; 1 above 5 s; 0 above 15 s) and then `k` timed calls follow, and the `note` column of `timings.csv` records exactly this per cell. Every cut is listed in the `times` cuts table.
- **Deviation 4, runstats alignment moved out of timing.** `runstats::RunningMean/RunningSd` return left-aligned windows (the window starts at i; the last n - 1 values are `NA`). The timed closure returns that raw result and only tags it in place (`attr(out, "rw_align") <- "left"`, plus the window width in `rw_window`, on the local fresh vector: no copy). `rw_normalize()` shifts tagged output to right-aligned, outside timing, before the correctness check. So runstats is now timed as the package returns it. (Round 1 timed the shifted result; its runstats figures at w=101 were mean 11.4 ms and sd 28.7 ms, against 8.09 and 25.9 now, so the shift was a sizeable part of the round-1 mean number.)
- **Deviation 5, argument choices the brief left open.** `RcppRoll::roll_medianr(fill = NA)` is used (right-aligned; plain `roll_median` is centred). The custom function is `sum_custom <- function(x) sum(x)`, a naive window sum (my reading of "unoptimised"; I did not have the post's exact body). Calls: `data.table::frollapply(x, n, sum_custom)` and `zoo::rollapply(x, n, sum_custom, fill = NA, align = "right")`.
- **Single-thread controls (new).** `data.table (1 thread)` is `setDTthreads(1)` for the cell (restored afterwards); `RcppRoll (1 thread)` is `options(RcppRoll.threads = 1)`; `roll (1 thread)` is `RcppParallel::setThreadOptions(numThreads = 1)` (restored to `"auto"`). The 1-thread entry is timed right after its default-thread entry on the same data, through the same harness, and is also checked for correctness. Thread settings as found, before any change: `OMP_NUM_THREADS` unset, `getDTthreads()` 12, `RcppRoll::roll_threads()` 24, `RcppParallel::defaultNumThreads()` 24 (`versions.csv`).
- **Correctness check (not in the post).** Results are computed outside timing, normalized (`as.numeric`, runstats shifted, left-pad with `NA`) and compared with `data.table::froll<stat>` via `all.equal(tolerance = 1e-8)` plus identical NA positions. cuplyr results are collected for this check only. A cell whose call errors counts as a failure in the table (it does not drop out of the count); there were none.
- **Fallback check.** `cuplyr_cpu_fallback` conditions are caught per cell: none was raised by the native `roll_*` and froll-alias entries; one was raised for `roll_median` (expected).
- cuplyr entries: `cuplyr` is native `roll_<stat>(x, n)` inside `mutate()`; `cuplyr (froll alias)` is `data.table::froll<stat>(x, n)` inside `mutate()` (cuplyr maps it to the same kernel; the alias was 0.004-0.081 ms slower than native in each of the 15 cells, i.e. within 0.1 ms); `cuplyr (CPU fallback)` is `roll_median()`, which has no cudf kernel in 25.12 and runs through an R loop on collected data (so that call includes its own download and upload). Custom: n/a (cuplyr cannot apply an arbitrary R function over windows).

## Per-call cost breakdown (overhead)

Measured on the same harness as everything else (gc-separated, fenced, `compute()` of an eager `mutate()`), on a 1e3-row table (kernel negligible; 50 samples) and, for contrast, on the 1e6-row table (20 samples). The per-statistic 1e3-row rolling floors are listed too.

{{tables-overhead.md}}

- **The ~2.0 ms floor is for window-function mutates; a plain mutate is about 1.3 ms.** At 1e3 rows: plain `mutate(y = x + 1)` 1.27 ms, `mutate(r = cumsum(x))` 1.96 ms, `mutate(r = roll_mean(x, 101))` 2.01 ms (the five rolling statistics: 2.01-2.07 ms medians; all 250 samples between 1.95 and 2.33 ms). `cumsum` costs the same as `roll_mean`, so the extra ~0.7 ms (37% of the floor) belongs to the window-function path, not to any one kernel.
- **What the path does (read from the code, confirmed with `show_query()`).** A plain mutate is one node (`ast_mutate` over `ast_source`). An eager window mutate is `ast_select <- ast_mutate <- ast_window <- ast_source` (`R/mutate.R` lines 617, 619 and 627 push the window, mutate and select nodes), and each node materializes a full table: `src/ops_window.cpp` ~line 1171 builds the window output by deep-copying every input column (`std::make_unique<cudf::column>(view.column(i))`). So `x` is copied three times per call, not once. I did not profile where the 0.7 ms goes (R-side node handling vs copies); that split is unknown at 1e3 rows.
- **GPU memory shows it, to the byte** (1e7 rows, `memory-breakdown.csv`):

{{tables-memory.md}}

  The 565,000,192 B held right after a `roll_mean` mutate decompose as 161,250,048 (window output: x + `..win1..` + validity mask) + 242,500,096 (mutate output: x + `..win1..` + `r` + two masks) + 161,250,048 (select output, the result) = 565,000,192. The decomposition is reasoned from the node chain and matches the measured total exactly; I did not measure the three tables separately. A plain mutate holds 160,000,000 B (x copy + `y`, one materialization) and allocates 160,000,220 B in total, against 726,265,705 B allocated by one `roll_mean` mutate. After a `gc()` the `roll_mean` result alone is 161,250,048 B, so about 3.5x the result is held while the intermediates await finalization.
- **The copy and allocation cost scales with rows and is inside every 1e6 and 1e7 cuplyr timing.** At 1e6 rows the plain mutate takes 1.47 ms (+0.20 ms vs 1e3 rows), the `cumsum` window mutate 2.62 ms (+0.66 ms) and `roll_mean(x, 101)` 3.12 ms (+1.11 ms). The narrow-window rolling mean (w=11, 2.78 ms in the tables above) is only 0.16 ms above the `cumsum` mutate: at narrow widths, most of cuplyr's time at this size is the call chain and the copies, not the rolling kernel. (This is an inference from comparing two different kernels, not a profile.)

## Conclusions (in the post's style, updated)

All figures: 1e6 rows, width 101, median ms, computation only. cuplyr excludes transfers. Thread behaviour of the CPU entries is the measured one in "Threads actually used": RcppRoll ran on 24 OpenMP threads; data.table's mean/sum/min/max/sd and `by=`, and roll, ran effectively on one thread; data.table's median and exact sum scale.

- **The post's headline ("data.table wins") holds at equal, one-thread conditions; RcppRoll's lead at default settings comes from its 24 OpenMP threads.** At default settings RcppRoll was the fastest package in every statistic: mean 0.87 ms (data.table 1.36), sum 0.87 (1.39), min 0.97 (2.31), max 0.99 (2.36), sd 1.10 (10.7), median 4.58 (19.3). With `RcppRoll.threads = 1` it takes mean 7.82, sum 7.79, min 11.2, max 11.1, sd 10.4 and median 65.2 ms (9-14x slower). Against that one-thread RcppRoll, data.table (whose mean/sum/min/max calls are single-threaded anyway) is faster for mean, min and max at all three widths (mean 1.36 vs 7.82 at w=101 and 1.34 vs 1.50 at w=11), for sum at w=101 and w=1001 (at w=11 it is 1.36 vs 1.40: data.table slightly ahead, non-overlapping IQRs), and for median at all three widths (28.2 / 44.6 / 65.0 ms at one thread vs 36.4 / 65.2 / 94.9); RollingWindow's median (33.4 / 52.6 / 66.7) is behind data.table at one thread at w=11 and w=101 and level at w=1001. Even with its 12 threads data.table's median (19.3 ms) is about 4x slower than the 24-thread RcppRoll (4.58). sd is the exception: RollingWindow (7.43 ms) is fastest, then one-thread RcppRoll (10.4) and data.table (10.7); the post had no data.table sd.
- **roll** (4.03 ms mean, 3.16 sum, 10.4 min/max, 23.4 sd, 221 median) is a reasonable choice for statistics it covers, but data.table 1.18 now has `frollmedian` and `frollsd` and beats it on those (at one thread, too: median 44.6 vs 221 ms, sd 10.9 vs 23.3). roll ran on one thread for every statistic.
- **slider** (48-53 ms at w=101; 28 ms at w=11, 69-78 ms at w=1001, growing with the width) is for custom alignment, not speed. **zoo** (113-452 ms) and **runner** (0.5-0.84 s at w=101, 3.0-6.6 s at w=1001) are slow. **Custom functions** cost 1.25 s (`frollapply`; 2.1 s at one thread) and 3.8-12.4 s (`zoo::rollapply`, growing with the width) against 1-2 ms for the optimized equivalents. Avoid them.
- **Where cuplyr lands (ungrouped, 1e6 rows).** Native mean/sum/min/max take 2.8 / 3.1-3.2 / 7.0-7.1 ms at widths 11 / 101 / 1001, of which about 2.0 ms is the per-call floor for window mutates. For mean that is faster than roll (4.03), RollingWindow (5.53), runstats, slider, zoo and runner at widths 11 and 101, and slower than data.table (1.36) and the 24-thread RcppRoll (0.87) at every width; at w=1001 it is also slower than roll (4.04) and RollingWindow (5.51) and level with one-thread RcppRoll (7.05 vs 7.07). Against one-thread RcppRoll cuplyr's mean is slower at w=11 (2.78 vs 1.50) and faster at w=101 (3.16 vs 7.82). For sum it matches roll at w=101 (3.16 each). For min/max it beats data.table only at w=11 (2.79 vs 3.34 and 2.78 vs 3.31 ms). cuplyr sd takes 3.43 / 8.11 / 54.8 ms: second at w=11, third at w=101, slowest of all at w=1001 (data.table 10.7, runstats 24.1). cuplyr `roll_median` takes 9.5 / 11.9 / 32.0 **seconds** per call (one timed sample each), a CPU fallback 500-1600x slower than data.table's 19-20 ms. Custom functions: not supported.
- **cuplyr's cost grows with the window width** (mean 2.78, 3.16, 7.05 ms; sd 3.43, 8.11, 54.8 ms) while data.table's mean/sum/sd, roll and the 24-thread RcppRoll's mean/sum/sd are flat in the width (data.table's min/max get faster with the width; its exact sum and RcppRoll's median get slower). That pattern is what a kernel that rescans each window would produce (sd goes up 6.8x for a 10x wider window). "The kernel is not incremental" is my inference from that scaling; I did not read or profile the kernel (F2).
- **Grouped data and large data, in the configurations measured here.** Grouped mean (one configuration: 1e6 rows, **1e3 groups**, w=101): cuplyr 3.65 ms vs data.table by group 28.2 ms and slider 55.1 ms, about 7.7x and 15x, computation only. data.table's `by=` evaluation ran effectively single-threaded (28.2 ms by default, 27.6 ms at `setDTthreads(1)`), so the 7.7x is the GPU against **one CPU thread making 1,000 per-group calls**, not against 12 threads. I did not vary the group count; data.table's cost is expected to grow with the number of groups, so the ratio is specific to 1e3 groups. At 1e7 ungrouped rows (one size) cuplyr is fastest at w=11 (6.01 ms vs 24-thread RcppRoll 9.48, data.table 18.2, roll 48.9; one-thread RcppRoll 20.1) and w=101 (9.70 vs 11.7 / 18.5 / 49.0; one-thread RcppRoll 83.8), and loses at w=1001 (48.0 vs RcppRoll 11.6 at 24 threads, data.table 18.5; level with roll 48.9). Peak GPU memory for the 1e7 call was 565 MB, well inside 12 GB, but see F1.
- Net: at the post's size cuplyr is mid-pack and bounded below by about 2 ms of per-call cost. In the two larger configurations measured (1e3 groups; 1e7 rows with windows of 11 and 101) it was the fastest entry, including against 24-thread RcppRoll at 1e7; that is one grouped configuration, one large size and narrow windows, and it loses at w=1001. All of it only when the data already lives on the GPU.

## Findings (candidate backlog rows; nothing was fixed in this feature)

- **F1. An eager window mutate materializes three full tables and holds them until R's GC.** One eager `mutate(r = roll_mean(x, 101))` on 1e7 rows runs ast_window -> ast_mutate -> ast_select (`R/mutate.R` 617, 619, 627); each node builds a new table and `src/ops_window.cpp` (~1171) deep-copies every input column, so `x` is copied three times. Right after the call 565,000,192 bytes are held (`gpu_alloc_tracking()`: held = peak) = 161,250,048 + 242,500,096 + 161,250,048, against 161,250,048 for the result alone, and 726,265,705 bytes are allocated in total (`memory-breakdown.csv`, `memory-finding.csv`). A plain mutate holds 160,000,000 bytes (one materialization). The intermediates are freed only when R finalizes their pointers: twenty back-to-back calls without `gc()` ran out of memory at the 20th ("GPU operation 'mutate' failed ... std::bad_alloc: out_of_memory: CUDA") on the 12 GB card, with the results dropped each time. Candidate row: remove the two extra materializations (append the window results directly to the input table instead of copying every input column; no full-table copies in the mutate and select steps, e.g. share the unchanged column buffers or fuse the three nodes). That would take the 1e7 call from 565 MB to about 161 MB (3.5x). Freeing per-call intermediates deterministically (or an automatic `gpu_gc()` and retry on `bad_alloc`) would remain a separate hardening.
- **F2. Rolling kernels slow down with the window width; sd is the worst.** At 1e6 rows mean goes 3.16 to 7.05 ms and sd 8.11 to 54.8 ms from w=101 to w=1001 (data.table is flat: 10.7 ms for sd). At 1e7 rows mean at w=1001 takes 48.0 ms vs data.table 18.5 and 24-thread RcppRoll 11.6. The scaling suggests the kernel rescans each window (inference; not profiled). Candidate row: an incremental mean/sum (prefix sums) and a Welford or sum-of-squares sd, checked against `all.equal(1e-8)`, or find a cudf 25.12 aggregation that does not rescan each window (needs a probe).
- **F3. `roll_median()` CPU fallback is an R loop: 9.5-32 s for 1e6 rows.** `roll_apply_generic` (`R/roll.R`) loops in R. Candidate rows: (a) cheap, call `data.table::frollmedian` (19-20 ms here at 12 threads, 28-65 ms at one thread across the three widths) inside the fallback; (b) real, a GPU rolling median (cudf 25.12 has no MEDIAN rolling aggregation).
- **F4. A fixed overhead of about 2.0 ms per eager window-function `mutate()` on a 1e3-row table (1.3 ms for a plain mutate).** About 0.7 ms of the 2.0 is specific to the window path, i.e. the window -> mutate -> select chain (three nodes, three materializations; `cumsum` costs the same as `roll_mean`), not any single kernel; the rest is the 1.3 ms every eager mutate pays. At 1e6 rows the same chain costs 2.62 ms for `cumsum` against 1.47 ms for a plain mutate, and the floor is about 70% of the narrow-window rolling cost. Candidate row (same fix as F1): remove the two extra materializations, then re-measure the 1e3-row floor; profile the remaining 1.3 ms plain-mutate cost (R dispatch, AST build, schema inference) separately, since I did not.
- **F5 (minor). No documented completion semantics.** Nothing in `src/` synchronizes, so wall-clock timing of cuplyr from R is only meaningful after a device-to-host read; the benchmark uses a one-row `gpu_head()` as a fence. Candidate row: a documented `gpu_sync()` or similar for benchmarking. Related: `x$ptr` on a `tbl_gpu` from outside the namespace returns `NULL` (tibble's `$`), so helper code has to use `.subset2()`.
